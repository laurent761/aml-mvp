00 / The idea

A laboratory for testing
what an agent actually does.

Give an attacker a controlled way to influence an agent. Run the agent in an isolated environment. Verify the effects, preserve the evidence, and compare experiments under the same conditions.

The platform supplies

Runnable targets, intervention delivery, isolation, independent verification, durable research records, the SDK and evaluation execution.

The researcher decides

Attacker model, prompts, training method, hardware and checkpoint loading. Training runs externally; real-model configuration is still a placeholder.

03 / From data to evaluation

Keep the chain
from experiment to checkpoint.

The platform records and connects research work. Your external process decides how to learn from it.

Start with a research run.

Pin the source-code revision and opaque configuration. Link datasets, an external tracking reference, a parent run or a resume checkpoint. Append lifecycle events rather than rewriting history.

POST /v1/research-runs
{ "name": "invoice-study",
  "code_revision": "your-commit",
  "execution_mode": "external" }

What gets recorded?

  • Exact supplied prompts, public history, raw model responses and parsed actions/errors.
  • Generated, replayed or search-selected provenance; model/runtime/checkpoint references.
  • Seeds, parent links, delivery receipts, observations, verified outcomes and usage.
  • Trainer artifacts such as token IDs, masks or log probabilities, when supplied.

Absent information stays absent. The platform does not invent missing prompts or trainer outputs.

What stays separate?

  • Default model-input exports exclude private outcomes, verifier measurements and rewards.
  • A reported training reward is an annotation; it cannot change the official outcome.
  • Test-containing runs are rejected from train-scoped exports.
  • Stored checkpoints have verified files and manifests; actual loadability is not asserted.

04 / Run it yourself

Start with the fixture.
Connect your model later.

Use the authenticated research demo for the end-to-end SDK workflow, or the complete stack for MinIO, MLflow and telemetry. The README has the full runbook.

Prerequisites: running Docker + Compose v2, Python 3.12+ and uv. First builds need network access. Use one active capsule supervisor per Docker endpoint.

1. Build the application images

From the project root, enter backend/. Python uses the locked backend dependencies; Docker shares build layers.

Terminal / backend
cd backend
uv sync --extra dev
docker build --target api -t adversarial-api:local .
docker build --target worker -t adversarial-worker:local .
docker build --target capsule-supervisor -t adversarial-capsule-supervisor:local .
docker build --target blue-gateway -t blue-gateway:local .
docker build -t adversarial-ui:local ../ui
2. Generate credentials and start services

Keep the generated files local. Reuse them on subsequent starts; the initializer refuses to overwrite them. On Linux, set DOCKER_GID to the socket's group if needed.

Terminal / backend
uv run python scripts/init_research_smoke.py
docker compose --env-file var/research-smoke.env -f compose.research-smoke.yaml up -d --wait
docker compose --env-file var/research-smoke.env -f compose.research-smoke.yaml ps

Open the UI at port 13000. In its connection dialog, use the same-origin proxy and paste the token from var/research-smoke.client.json.

3. Register the reference bundle

This operator command stores the private bundle in the database. Only its public scenario is exposed through the research catalog.

Terminal / backend
uv run adversarial-bundle build-reference --output var/bundles/finance-reference.json
docker compose --env-file var/research-smoke.env -f compose.research-smoke.yaml cp var/bundles/finance-reference.json api:/tmp/reference.json
docker compose --env-file var/research-smoke.env -f compose.research-smoke.yaml exec -T api python -m adversarial_agent_mvp.bundle_cli register /tmp/reference.json
4. Install the SDK and run the acceptance workflow

Runs benign/attack fixtures, reset, export, checkpoint round-trip, paired evaluation, reproduction and UI record checks. No real model or GPU is required.

Terminal / backend
uv venv var/sdk-acceptance
uv pip install --python var/sdk-acceptance/bin/python ../sdk
var/sdk-acceptance/bin/python ../sdk/examples/acceptance.py --connection var/research-smoke.client.json --output var/acceptance.json
5. Inspect logs and stop while preserving data
Terminal / backend
docker compose --env-file var/research-smoke.env -f compose.research-smoke.yaml logs --tail=100 api worker supervisor
docker compose --env-file var/research-smoke.env -f compose.research-smoke.yaml down

Only add -v when intentionally deleting this profile's database and artifacts.

Start the complete local stack

This profile includes MinIO, MLflow and the telemetry collector. It reads .env and uses different ports and volumes. Do not run it alongside another active AML supervisor on the same Docker endpoint.

Terminal / project root
cd backend
test -f .env || cp .env.example .env
# Review .env before starting.
docker compose up -d --build --wait
docker compose ps

# Later: stop without deleting data.
docker compose down

Development defaults are local-only. To use authenticated SDK access, configure RESEARCH_AUTH_REQUIRED and the hashed RESEARCH_AUTH_TOKENS principal map. The generated research-demo token is not automatically valid here.

05 / What is implemented

The infrastructure,
from bundle to comparison.

Expand a phase to see its responsibility. Implementation and fixture validation are distinct from acceptance with a researcher-selected real model.

INF-01Runnable targets + scenario catalog

Digest-pinned target bundles, versioned scenario assets, a public catalog and private ground truth. A synthetic finance reference agent supplies a complete fixture workflow.

Bundle guide ↗
INF-02Target inference integration

A trusted supervisor broker relays target model calls with scoped access, pinned settings, limits and metering. Real provider/model/credentials remain unselected.

Inference guide ↗
INF-03Explicit intervention delivery

Messages, named documents and declared tool-result slots use validated schemas and delivery receipts. Injected content cannot fabricate trusted virtual-world events.

Intervention contract ↗
INF-04Durable research sessions

External and managed execution share reset/step commands. Ownership, expected indices, idempotency, leases, fencing, heartbeats and cleanup bound execution.

INF-05Independent Python SDK

Async session cleanup, typed results/errors, bounded retries/concurrency, operation recovery, data transfer and executable examples without backend imports.

INF-06Outcomes and rewards

Separate public observations, authoritative outcomes, versioned measurements, baseline rewards and optional researcher-reported annotations.

INF-07Recording and dataset snapshots

Exact generation records and source lineage feed immutable JSONL/Parquet snapshots. Failures and partial runs remain explicit; test data is excluded from train-scoped exports.

INF-08External runs and checkpoints

Connect code, config, data and external training lifecycle. Stream large uploads/downloads, validate checksums and atomically publish complete checkpoint manifests.

INF-09Approved attacker runtimes

Operator-controlled endpoints and secret references, versioned identities, health checks and checkpoint attestation on responses. Ranking is optional.

INF-10Executed evaluation + reproduction

Frozen suites drive matching baseline/candidate sessions and persisted comparisons. Fresh replay records reproduction and divergence, not a promise of determinism.

INF-11Access and operational limits

Bearer scopes and ownership checks, atomic owner quota reservations, storage/request limits, cancellation, failure reporting and component health.

INF-12UI and deployment integration

The existing navigation reads SDK-created sessions, trajectories, outcomes, evidence, runs, datasets, checkpoints and evaluations. Deployment and acceptance examples are packaged.
